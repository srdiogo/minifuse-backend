# Local control protocol v1 — draft

This is the canonical implemented API v1 candidate for both desktop clients.
Freeze a stable release only after service/client and hardware acceptance tests.
Use one published spec/fixture revision; do not maintain separate client specs.

## Transport and envelopes

UTF-8 JSON objects separated by LF on the Unix socket documented in
[the architecture](ARCHITECTURE.md). On the wire each frame is one line; the
examples below are formatted for reading. Maximum frame size: 256 KiB including
LF. Reject invalid UTF-8, nonfinite numbers, duplicate object keys, oversize
frames and unknown request fields. A partial frame has a two-second deadline. At most 16 connections and 32
outstanding request IDs per connection are admitted. Invalid framing closes
the connection; error delivery for an unparseable frame is best effort.

Requests have `api`, `id`, `method`, `params`. API major is integer `1`; IDs are
nonempty client-chosen strings of at most 128 characters, unique among that
connection's outstanding requests. `params` is always an object. Responses
carry the same ID and exactly one of `result` or `error`. Events have `event`,
`epoch`, `seq`, `data` and no response ID. Unknown response/event fields may be
ignored for additive minor revisions; clients must handle unknown event names.

```json
{"api":1,"id":"hello-1","method":"hello","params":{"client":"minifuse-control","supported_api":[1]}}
```

```json
{"api":1,"id":"hello-1","result":{"selected_api":1,"service_version":"0.1.0-dev","epoch":"example-epoch","client_token":"example-token","features":["plans","subscriptions"]}}
```

Version strings/tokens above are illustrative, not an existing release. A
reconnecting client may present its previous client token to query its durable
operation identities, subject to same-UID validation. Tokens are opaque,
generated by the service, and not accepted as commands or filesystem names.

## Identity and revision

Every device operation includes `device_id` and `generation`. IDs are opaque
within the service epoch. `revision` is an opaque token representing the exact
confirmed complete state. Never derive any of these from a UI row, USB address
or a stored preset. Plans include epoch/generation/revision and expire after
30 seconds. A reconnect always invalidates them.

## Methods

| Method | Parameters | Result |
|---|---|---|
| `hello` | Client name, supported API majors; optional previous client token | Negotiated major, version, epoch, client token, protocol features |
| `list_devices` | Empty | Inventory with model, connection state, capabilities, versioned presentation profile and limitations |
| `get_model_profiles` | Empty | Read-only model catalog; no device read or write |
| `get_state` | Device ID and generation | Confirmed revision, decoded state and capability metadata |
| `subscribe` | Event names; optional device ID/generation | Subscription ID, current sequence and full relevant baseline |
| `plan_changes` | Device ID, generation, expected revision, domain changes | Plan ID, predicted state, changes summary, expiry and omitted differences |
| `plan_restore` | Device ID, generation, revision, bounded snapshot content, optional mix | Same plan result; unsupported fields reported |
| `begin_control` | Device ID/generation, expected revision, fixed target, idempotency key | Durable pending gesture operation |
| `update_control` | Operation ID, contiguous sequence, value, finish flag | Admission receipt; settlement by event/query |
| `cancel_control` | Operation ID | Terminal gesture result; confirmed changes are retained |
| `apply_plan` | Plan ID and idempotency key | Accepted operation ID; completion comes via event/query |
| `get_operation` | Operation ID or the client's idempotency key | Pending/completed/indeterminate outcome and known verification details |
| `capture_snapshot` | Device ID, generation | Schema-1 snapshot content from a confirmed read; no device writes |
| `inspect_snapshot` | Bounded snapshot content | Offline decoded data, model/layout validity and supported restore scope |
| `list_presets` | Empty | IDs/names/model/schema metadata under the designated preset directory |
| `save_preset` | New display name and bounded valid snapshot content | Exclusive newly assigned preset ID; no overwrite |
| `load_preset` | Preset ID | Snapshot content; no device writes |

Snapshot decoded size is bounded to the existing 64 KiB. Do not accept a path in
place of content. Named presets are host files, not device-flash saves. Restore
always requires planning and explicit apply. A preview never acquires write
access solely because it could eventually be applied.

`get_state` on a product without established B2 support returns
`unsupported_capability`; inventory remains available. No v1 method exposes
raw USB, raw selectors, firmware, module loading or a fabricated meter value.
Legacy toggles are a future explicit capability, not a generic escape hatch.

## Domain changes

`plan_changes` accepts a bounded array of typed operations:

- `channel`: mix, source and at least one of `level_db`, `pan`, `mute`, `solo`.
- `master`: mix and `level_db`.
- `route`: mix and a route name supported by the returned capabilities.
- `membership`: mix, supported analog mono/USB pair name and `included`.

Use existing names `out12`, `out34`, `loopback`, `analog1`..`analog4` and
`usb1`..`usb6` subject to mix/model gates. Membership uses USB pair names.
The service delegates allowed combinations to the core and never broadens them.
Gain ranges are the existing source −60..+12 dB and master −64..0 dB. JSON null
for a present `level_db` means −infinity; an omitted field means preserve it.
Pan is 0..1. Null in confirmed derived level/pan means silence/undefined as
documented by the core; it must not be rendered as 0 dB or center silently.

```json
{"api":1,"id":"plan-1","method":"plan_changes","params":{"device_id":"device-example","generation":"generation-example","expected_revision":"revision-example","changes":[{"kind":"channel","mix":"out12","source":"analog1","level_db":-6.0,"pan":0.5}]}}
```

Plans cannot be edited or transferred to another client. Reject overlapping
domain fields/duplicate selectors rather than relying on request order. The
core validates the final bounded selector plan, including rollback originals.
Source removal's mute/solo side effects appear in the plan summary.

## Results and errors

The confirmed operation outcome is one of `verified`, `failed_restored`,
`failed_unrestored`, `unknown`, `rejected`. A live gesture closed before any
sample uses `not_attempted`. While admitted/queued/executing,
the operation status is pending and has no invented terminal outcome.

Return separate fields for `device_outcome`, `rollback_attempted`,
`rollback_verified`, `after_state_valid`, `journal_status` and an opaque
operation reference. This allows a verified write with failed journal
finalization to be represented honestly. Never equate an acknowledgement,
attempted rollback or saved host file with a verified final device state.

Error shape:

```json
{"api":1,"id":"apply-1","error":{"code":"stale_state","message":"Device state changed; refresh and create a new plan.","details":{"device_write_attempted":false,"refresh_required":true}}}
```

Required codes: `invalid_request`, `unsupported_api`, `unsupported_capability`,
`access_denied`, `device_unavailable`, `ambiguous_device`, `module_incompatible`,
`stale_state`, `device_changed`, `plan_expired`, `plan_unknown`,
`idempotency_conflict`, `queue_full`, `backup_failed`, `operation_failed`,
`journal_failed`, `control_busy`, `control_closed`, `outcome_unknown`, `subscriber_overflow`, `internal_error`.
Messages explain recovery; clients branch on codes/fields, not English text.
An error never instructs the GUI to rerun a mutation automatically.

## Events and subscription ordering

Events: `device_added`, `device_removed`, `capabilities_changed`, `state_changed`,
`operation_started`, `control_updated`, `operation_finished`, `control_panel_requested`.
The button event is advertised only with validated capability evidence.

`subscribe` registers the stream and captures its baseline/sequence atomically
within the coordinator. One subscription is allowed per connection. Later
events have contiguous sequence numbers within that filtered subscription and
service epoch, starting after the returned sequence; unrelated filtered events
do not create gaps. Clients apply no pre-baseline deltas. Detect gaps, overflow and
epoch changes; reconnect and obtain a complete baseline rather than guessing.
Initial reads/reconnection do not synthesize button or operation events.

`control_panel_requested` contains device identity and a unique event ID, not
an executable command or an Omarchy-specific target. One desktop agent owns
activation policy. Multiple UIs can subscribe to state without all opening in
response to the same hardware event. Its data contains `device_id`, `generation`,
`event_id`, `source: "arturia_logo"` and `gesture: "short_press"`. Subscribe only
when runtime `capabilities.control_panel_button` is true. Support currently
covers normal-mode MF4 with USB firmware descriptor 1.0.1 and a confirmed
counter; see [evidence, polling and reset rules](mf4/logo-button.md).

## Retry and compatibility rules

Read methods may be repeated after reconnection with fresh identity. For an
uncertain `apply_plan`, query its durable operation identity; never send a new
key to repeat the write. Unknown post-crash prepared records require explicit
reconciliation. A reused key with different content is rejected.

Additive fields/events can extend API v1 with capability negotiation. Changed
meaning, framing, identity or mutation guarantees require a new API major.
Freeze example fixtures with the first implementation tag; future clients pin
that spec artifact and execute the same success/error/lifecycle contract tests.


## Implemented result shapes

- Inventory returns `{ "devices": [...] }`. Each entry carries `device_id`,
  `generation`, model, connection, capabilities and an optional structured error.
- State returns `device_id`, `generation`, `revision`, decoded `state` and
  capabilities. Gains/pan remain configured values; signal meters use separate ephemeral events.
- Plans return `plan_id`, epoch/identity/revision, `expires_in_ms` (30000),
  `predicted_state` and `summary` (including omitted restore byte offsets).
- Apply acknowledges a durable `operation_id` with status `pending`. The
  completion event/query has status `completed` or `indeterminate`, and separate
  device/recovery/journal facts. Internal client tokens/request digests are not
  broadcast. A metadata-finalization failure can retain a known in-memory
  device result; after restart a prepared record has unknown outcome.
- Subscribe returns `subscription_id`, epoch, `seq`, inventory and confirmed
  `states` as one atomic baseline. Reconnect to change filters.
- Capture/load return snapshot JSON as a bounded string. Save assigns an opaque
  preset ID and never overwrites an existing file. Inspect returns decoded
  state/schema/layout/capability metadata without accessing hardware.

Canonical complete examples are in `tests/contract/v1.json`. Unknown API majors,
fields, kinds and unavailable event subscriptions are rejected explicitly.
`device_write_attempted: null` represents uncertainty, not false.

## Continuous controls

`hello.features` advertises `live_controls`. The service accepts one active
gesture at a time; normal new apply requests return `control_busy` during it.
The immutable `target` is one of:

```json
{"kind":"channel_level","mix":"out12","source":"analog1"}
{"kind":"channel_pan","mix":"out12","source":"analog1"}
{"kind":"master_level","mix":"out12"}
```

Begin takes `device_id`, `generation`, `expected_revision`, `target` and
`idempotency_key`. Update takes `operation_id`, `sequence` (1..512), `value`
and `finish` (boolean). `value` is required: a gain number or null for silence;
pan requires a number in 0..1. Existing model, mix and gain limits apply.
An identical retained sequence returns the same admission receipt without a
second dispatch; changed reuse is rejected. The receipt is not a completion.
Only one sample can be pending. A closed/reconnected gesture cannot resume.

`control_updated` carries the durable operation record after an intermediate
sample settles: `status: pending`, `sample_sequence`, last sample verification
facts and bounded accepted `samples`. A final sample emits
`operation_finished` with `gesture_end: finished`. Other terminal reasons are
`cancelled`, `disconnected`, `expired`, `conflict`, `failed`, `sample_limit` or
post-crash `interrupted`. None claims that an unsent final pointer value was
applied. The gesture's `device_write_attempted` covers any admitted sample;
rollback/state/journal facts describe the last settled sample. Per-sample core
records remain in `backup_group`, including the initial baseline.

State events for a verified sample equal to its complete predicted readback
include that gesture's `operation_id`. Clients can preserve the active preview
on those events; unassociated changes still invalidate the old edit. The
kernel's full-state guard remains authoritative. Lease and coalescing behavior,
evidence retention and recovery are specified in [LIVE_CONTROLS.md](LIVE_CONTROLS.md).

## MF4 input switches

Confirmed `state.inputs` has boolean `inst1`, `inst2` and `phantom_power` fields.
`switch_readback` is model-specific; `input_switches` additionally requires the
active module feature. It must not be inferred from the model or remembered
commands. The standard state subscription reflects physical switch changes.

`plan_changes` accepts `{"kind":"input_switch","target":"inst1","enabled":true}`.
The other targets are `inst2` and `phantom_power`; the last is shared by physical
inputs 1–2. Only booleans are accepted. These use ordinary immutable plans,
durable operation admission, complete-state verification and outcome recovery.
They are discrete actions, not continuous-control targets. Module feature
changes invalidate outstanding plans and publish capability/state updates.
Snapshot restoration continues to exclude these switches.

## Signal meter subscription

Negotiate `signal_meters` in `hello.features`, then include `meters_updated` in
`subscribe.events`. Each event carries device ID, generation and `available`.
When available, `sources_dbfs` has 10 values (Analog 1–4, USB 1–6) and
`mixes_dbfs` has three stereo pairs (out12, out34, loopback). A null value means
digital silence; numbers are finite peak dBFS at or below zero. Mix peaks are
post-master and before destination route selection. They are not physical
output meters when a destination bypasses its mix.

The runtime `signal_meters` capability requires the mapped MF4 layout and the
module's fixed C2 query. No USB meter reads occur without a matching subscriber.
Polling targets at most 20 Hz; blocking control calls can delay it. Failures
publish `available:false` and back off for one second. Identity mismatch never
attaches a frame to the old device. Meter events do not change configuration
revisions, invalidate plans or produce snapshots/journals. They share existing
bounded event queues and disconnect-on-overflow behavior; stale data must clear
in clients (the application uses a 500 ms freshness timeout). No frame is
replayed after reconnect.

## Model profiles and experimental basic state

Inventory includes `profile` with `schema_version: 1`, stable `id` (`mf1`, `mf2`,
`mf2_otg`, `mf4`), `device_mode`, `layout`, physical I/O counts, `input_controls`,
`hardware_validation` and notes. It remains present when transport is disabled.
`get_model_profiles` returns `{schema_version: 1, profiles: [{product_id, profile}]}`.
Profiles select presentation; they do not grant any read/write capability.
Unknown profile schemas/layouts must not enable controls. Multiple recognized
interfaces require explicit selection; bundled clients leave controls unavailable.

For compatible MF1/MF2/OTG devices, `state.layout` is
`minifuse-basic-b2-v1`, `mixes` is empty and `inputs` contains Boolean `inst1`,
`phantom_power`, `direct_monitor`, and `inst2` for two-input models. `mixer`,
`signal_meters` and `host_snapshots` remain false. `switch_readback` requires
confirmed basic state; `input_switches` additionally requires matching module
support. `input_switch` changes use the existing plan/apply operation with
`target: direct_monitor` as an additive target, labeled direct mono on MF2/OTG.
This basic-only mode does not expose live faders or presets. Complete-state
revisions and durable outcomes retain their existing semantics.

Initialization/storage modes have `layout: initialization`, no input controls
and no audio capability. See [model support](models/README.md) for the separate
46/52-byte driver ABI, firmware gate, evidence and acceptance requirements.

### Firmware-gated native loopback

`list_devices` additionally reports `firmware` with `version`, `raw_bcd`,
`source: usb_device_descriptor`, `loopback_compatible`, `required_family` and
`hardware_validation`. Compatibility is model-specific, not permission.

With compatible confirmed firmware, exact state and matching
module features, the runtime profile becomes `loopback_mixer`. Its state keeps
`layout: minifuse-basic-b2-v1` and adds `firmware`, one `loopback` mix, independent
`loopback: {enabled, usb12, monitor}` flags and an OTG-only `otg` object. `mixer`,
`host_snapshots` and `signal_meters` reflect actual module support. Source names
are analog1, analog2 when present, usb12, and usb34 (MF1/MF2) or usb56 (OTG).

Use the existing channel/master and live-control methods for gain, analog pan,
mute and master. USB pairs link gain/mute and expose `pan_available: false`.
`mute_mixed`/`level_mixed` flag inconsistent stereo-pair state; the next deliberate
linked adjustment changes both sides. Solo, membership, stereo pan and MF4
route operations are unsupported for this layout.

Additive discrete changes are:

```json
{"kind":"loopback_routing","enabled":true,"usb12":false,"monitor":true}
```

```json
{"kind":"otg_routing","main_to_otg":1,"otg_to_monitor":false,"meter_source":3}
```

Fields are optional but at least one is required. Booleans/unsigned integers are
strict; explicit null is invalid. OTG fields are rejected on other models. The
source guide specifies each enum. These changes use ordinary plan/apply, full
state preflight, durable outcomes and bounded rollback.

Model snapshots use `layout: minifuse-basic-loopback-b2-v1` and required
`firmware_bcd`. Restore requires the same PID and compatible firmware family;
only mapped mixer/routing fields are selected. Input modes, phantom, direct
monitoring and opaque bytes are preserved. Existing MF4 snapshot serialization
is unchanged and cannot be used for another model.

Model meter events retain the identity/generation and ephemeral semantics of
`meters_updated`, with `meter_layout: minifuse-basic-c2-v1`, `available`,
`inputs_dbfs` (one MF1 input, two otherwise), `loopback_dbfs` (L/R), `otg_dbfs`
(L/R on OTG, null otherwise). Missing/stale samples are unavailable, not zero.
These are not the MF4 ten-source/three-mix arrays. See the generated
[synthetic wire fixture](models/loopback-v1.json) and [evidence](models/EVIDENCE.md).
